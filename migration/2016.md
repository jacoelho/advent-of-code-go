## Source corrections

- Day 4 excludes decoy rooms before decrypting the storage-room name.
- Day 8 uses the specified 50×6 screen and computes the displayed text.
- Day 10 retains bot routing rules after a delivery; repeated firings and equal-valued chips are supported.
- Day 14 checks every quintuple in each future hash, while using only the candidate’s first triple. The window is exactly the following 1,000 hashes.
- Day 16 leaves an already odd-length checksum unchanged.
- Day 20 counts the allowed tail through address 4,294,967,295.
- Day 22 checks when its reduced state is sound and otherwise tracks actual payload movement, including merges.
- Day 24 derives the locations from the maze rather than assuming eight labels and counting floor tiles as visited locations.

## Design and reference comparison

Days 1–8 use direct movement, explicit keypads, triangle arithmetic, frequency ordering, sequential digest-nibble checks, column counts, segmented address matching and a dense screen. The [Python references](../reference/.repos/jpverkamp--advent-of-code/2016) informed keypad and screen handling; the [Haskell references](../reference/.repos/takemyoxygen--advent-of-code/2016/hs) supported direct ordered hash search and explicit bracket segments.

Days 9–16 were compared with the [Scala solutions](../reference/.repos/maneatingape--advent-of-code-scala/src/main/scala/AdventOfCode2016). Decompression computes lengths with an explicit stack. Bot deliveries use a queue. Elevator search canonicalizes complete generator/chip pairs, preserving safety relationships that per-floor counts lose. The office maze uses bounded breadth-first search. Hash matching uses a fixed 1,001-entry ring and sixteen counters. Disc timing uses generalized CRT. Dragon data is truncated to the requested disk size and its checksum reduced in place. Source shortcuts that lose chip identities or ignore later quintuples were rejected.

Day 17 retains the whole path because it controls door hashes; shortest and longest searches stop at the vault. Day 18’s four trap cases reduce to unequal left/right neighbours. Day 19 uses integer powers rather than floating logarithms. Day 20 sums gaps between sorted ranges. Day 21 reverses operations, retaining all valid predecessors of position-based rotation until the result is unique; this replaces the original 8! permutation search. Day 24 computes pairwise distances with the existing BFS helper, then solves the location tour by subset dynamic programming. The [Clojure inverse-scramble reference](../reference/.repos/tschady--advent-of-code/src/aoc/2016/d21.clj) and Scala pairwise-distance tour were useful; neither a hardcoded label range nor an arbitrary inverse choice was adopted.

## Shared interpreter and exact search

One Assembunny parser and machine owns days 12, 23 and 25. Each run clones the program. Invalid destinations are no-ops, toggle semantics follow instruction arity, and jumps may leave either end of the program. Addition and multiplication shortcuts inspect the current instructions, require positive terminating counters and distinct modified registers, and reject a changing multiplication source. No cached shortcut survives a toggle. Tests cover aliasing, nonpositive counters, invalid toggled instructions, self-toggle and independent runs. QA compared accelerated execution with literal execution for manageable day 23 seeds. The Go performance specialist found no material issue or simpler justified replacement; 259 accelerated oracle steps for seed 12 establish algorithmic sufficiency, not a measured Go speedup.

Day 25 searches positive seeds in order. Its proof key contains registers, instruction pointer, opcode image and expected next bit; operands cannot change under toggling. A repeated state is accepted only if the cycle emitted output. Finite good prefixes and silent cycles are rejected. QA independently proved seed 198 with a 12-output cycle and rejected every smaller nonnegative seed, including zero. The [clock specification](https://adventofcode.com/2016/day/25) requires the lowest positive seed.

Day 22 uses `(goal, empty)` states only when there is one empty node, every movable payload fits every movable node, no two movable payloads can merge, and the remaining nodes cannot send or receive data. The actual capacities are 85–94, positive movable payloads 64–73, wall payloads at least 490, and wall availability at most 20. These inequalities justify compression. The existing A* helper finds the shortest transfer sequence; its heuristic counts the minimum goal moves plus empty-node travel before the first such move. Outside that proof, breadth-first search tracks the full used vector and goal marker, permitting transfers into occupied nodes. Tests require such merges and reject an access node too small for the goal payload. An advisor reviewed both this reduction and the clock proof.

Resource exhaustion returns an error, not a guessed answer: vault searches allow one million queued paths and 128 MiB of cumulative passcode/path bytes; a VM run holds at most one million states; the clock search shares ten million work units across candidates, charging for each candidate and machine step. Day 22 allows one million compact expansions; its exact-search state limit scales with node count using a 128 MiB state-storage estimate. Elevator, bot, office-maze and hash searches also have explicit limits. These limits cover all original inputs and tested examples; unusual larger inputs may return a budget error.

## Shared OCR and 2019 correction

`aoc.Decode6RowDisplay` reads six-row glyphs in explicit four- or five-column cells. Its font masks were compared with [the collected C# font reference](../reference/.repos/CameronAavik--AdventOfCode/csharp/Common/OCR.cs). It supports full-width glyphs such as Y and rejects unknown shapes. Day 8 now derives `ZFHFSFOGPO` from its screen. Reusing the helper in 2019 day 8 removed its stdout print and hardcoded `YGRYZ` return. A separate literal two-layer `YAZAZ` image verifies transparency, opaque-zero precedence and a different computed answer.
